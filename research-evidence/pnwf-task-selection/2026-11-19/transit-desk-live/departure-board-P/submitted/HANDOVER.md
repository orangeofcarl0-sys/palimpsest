# DB-17 交班说明

## 修复结论

`board.mjs` 的站牌查询已修复：不再只展开查询时刻所在的自然日，也不会把所有凌晨班次笼统挪到前一天。查询现在按班次所属的**服务日**展开时刻表，同时保留午夜两侧的两类服务。`feed.json` 未修改，原接口 `departures(feed, stop, start, minutes)` 及返回字段保持不变。

## 投诉复现

修复前，周六 00:00 刷新站牌：

```sh
node cli.mjs River 2025-07-05T00:00:00Z 30
```

只会返回周六自己的临时加班车 `X3`，周五末班车 `R7` 看不到。上一版若把所有凌晨班次都归到前一天，则会反过来丢掉 `X3`。

修复后，同一条命令返回：

```json
[
  {
    "tripId": "R7",
    "serviceDate": "2025-07-04",
    "departure": "2025-07-05T00:12:00.000Z"
  },
  {
    "tripId": "X3",
    "serviceDate": "2025-07-05",
    "departure": "2025-07-05T00:19:00.000Z"
  }
]
```

两类服务都在：`R7` 是周五服务日里钟面 `24:12:00` 的末班车，实际在周六 00:12 发车；`X3` 是周六服务日的临时加班车，实际在周六 00:19 发车。周六常规班次 `S1` 不出现，是因为 `exceptions` 中 `SAT` 在 `2025-07-05` 被设为 `active: false`。

## 如何区分午夜两侧的服务日

- 返回结果中的 `serviceDate` 是班次所属的服务日；`departure` 是实际 UTC 发车时刻。两者可能相差一个自然日。
- 钟面 `< 24:00:00`：实际发车在 `serviceDate` 当天。
- 钟面 `>= 24:00:00`：实际发车在 `serviceDate` 的次日。例如 `24:12:00` 表示次日 00:12，`47:59:59` 表示次日 23:59:59。
- 因此判定午夜两侧时，不能看“发车时刻是不是凌晨”，而要看班次属于哪个服务日并换算实际发车时刻。`R7` 的 `serviceDate` 是周五、实际发车在周六；`X3` 的 `serviceDate` 和实际发车都在周六。
- 查询会从窗口起始自然日的前一天开始，覆盖延续过午夜的上一服务日，同时展开窗口覆盖的自然日；每个候选服务日都单独应用 `calendar` 和 `exceptions`，再按实际发车时刻过滤 `[start, start + minutes)`，左闭右开，并按实际发车时刻、再按 ASCII `tripId` 排序。这样窗口跨午夜时，前一天延续过来的班次和当天自己的班次都会被保留。
