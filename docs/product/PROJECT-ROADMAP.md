# Palimpsest 项目发展路线图

2026-11-10 · 主线基线 `2340fbb3edd5ec4ad57629d6c42377e2b308f098`

Palimpsest 面向会跨越多个 Session、持续变化的项目。用户表达目标、限制和交付要求。Agent 可以直接工作，也可以寻找独立判断或委派执行。新证据到来时，项目能指出哪些旧成果仍可使用、哪些决定需要重做，并让下一位参与者从可核查的成果继续。

《Palimpsest 整体规划与反思》把项目成果、Agent 互补和现实反馈放在同一个目标下。当前开发顺序是先补齐会妨碍接续的交付缺口，再验证正常产品入口中的自主协作。后续架构取舍依据任务质量、返工和人工协调的全周期观测。[产品交互模型](PALIMPSEST-INTERACTION-MODEL.md)

## 产品路径与职责

普通路径使用原生 DSH 推理、Git、Shell 和测试。ProjectWorkspace、Pulse 与 Continuity 从已有所有者读取目标、成果、未决问题与当前依据。下一次 Session 优先看到足以决定下一步的状态，详情按需读取。持久化对象包括可定位的成果、来源、适用条件、未决假设与失败记录。接受状态和当前适用性分别判断。[项目工作区与交互](PALIMPSEST-INTERACTION-MODEL.md) · [语义所有者](../engineering/architecture/SEMANTIC-OWNER-MAP.md)

协作规模与治理强度分别选择。一个 Agent 可以直接完成并提交。几个 Agent 可以并行调查、提出反例或接手部分成果。需要隔离写入、正式结算或受保护接受时，由既有 Work、Execution World、Evidence、Basis Admission 和 Promotion 承担对应合同。Git 提供版本事实，产品 Head 表示正式项目基线，Operator 决定需要批准的接受。模型负责需要判断的部分，程序负责可确定的检查、等待和状态转移。[Work 和 Continuity 产品路径](../programs/pc1/S02-NORMAL-PATH.md) · [审核与权限](../programs/pc1/S04-REVIEW-AND-AUTHORITY.md)

## 三个产品里程碑

| 里程碑 | 用户能完成的工作 | 进入下一步的证据 |
| --- | --- | --- |
| 一　可靠接续 | 在同一项目里先直接交付，现实变化后继续修订。确需正式执行时完成隔离、结算和接受。全新 Session 从可核对的成果继续。 | Energy 工程链已观察到。普通业务提示下分别实测直接与受治理路径，确认交付 SHA 可取回、有效成果可保留、受保护接受和自然结束各有证据。 |
| 二　自主协作与成果合成 | Agent 发现一个重要反证或缺口，吸收另一参与者的发现，调整实际成果，并复用仍适用的旧工作。 | 软件与非软件项目各有可追溯的发现、决定、实际产物和独立验证。模型自行选择合作时机。用强原生对照检验这条链产生的实际收益。 |
| 三　按任务选用能力 | 根据项目持续时间、依赖和风险选择直接工作、轻量项目上下文、独立执行或正式接受。 | 在重复配对中画出适用范围，区分上下文复用、认知协作与治理各自的收益和成本。跨项目 Ask 和长期经验回流在此之后按真实复用需求验证。 |

里程碑一的交付边界修复与里程碑二的试点使用同一条纵向任务。Energy 现有复现用于确认基础链路，新增真实样本优先回答自主合作能否改变成果。跨项目阶段继续沿用显式 Ask、耐久传输和项目各自的权限，观察引用是否减少重新调查以及引用是否经接收方独立采纳。[跨项目交互](PROJECT-TO-PROJECT-INTERACTION.md)

## 下一轮实施顺序

### 核对交付引用

先复现 Energy 两条接续 T3 暴露的引用错配。`DELIVER` 中的文件摘要值匹配新提交的 blob，`commit` 字段却指向先前的接受版本。`makeArtifactObserver` 在已安装的观察器上记住首次读取的 HEAD，后续 blob 读取仍解析当前 `HEAD:path`。先观察 A、原生提交 B、随后交付的回归可检验这一解释。[T3 核验](../engineering/ENERGY-PROJECT-CONTINUITY.md#摘要提交和退出) · [工件观察实现](../../src/composition/continuity.ts)

让一次观察使用同一个明确的 Git commit 读取工件并计算摘要。通过 `git cat-file` 证明发布的 `commit:path` 可取回同一字节。覆盖同一 Host 内的 A 到 B、工作树未提交修改、Attempt Result 及后续 HEAD 漂移。Episode 基线与工件提交分别复核，正式接受走现有 Head 和 Operator 路径。历史回执和原判分继续作为回归输入。第一批验收使用 [Episode 回归](../../test/alhs_episode_convergence.test.ts)、[Direct 到 Governed 回归](../../test/pnwf_cq_direct_governed.test.ts) 和 [Basis Admission 回归](../../test/pnwf_cq_basis_admission.test.ts)。

### 冻结一个软件接续试点

选用现有 gRPC 迁移夹具。首会话直接交付可运行版本。第二会话注入一份事先冻结的消费者兼容记录或可重放探针，使旧方案中一项假设需要重新验证。业务任务要求形成修订、保留仍通过的行为和测试，并按用户设定的风险边界送审。第三会话从经核验的版本完成一次交接。冻结变化前先选定必改产物、应保留的行为和一个会被旧实现触发的反例。把探针答案、评估器与 `expected/` 留在宿主侧，模型侧只见项目材料和合理的公开检查。[gRPC 迁移任务](../../fixtures/psvr/grpc-migration/TASK.md)

软件试点找出关键路径和失效模式后，再用 Energy 检查迁移性。第二领域复用容量、证书、成本和排程的交叉依赖，使用一份新变化及冻结的受影响范围。验收从实际来源、未受影响成果的 blob 和独立重算取得。若交付需要精确来源引用，在冻结的业务要求里给出该约束。已经验证过的 2026-11-06 更正及其 T3 严格判分用作回归。[Energy 任务与来源](../../fixtures/psvr/energy-deployment/TASK.md) · [严格判分](../../scripts/pnwf/energy/contract.mjs)

### 先验证两组运行条件

用现有 PNWF 容器、账本和轨迹归因从复制的项目状态各跑一次 Mock 闭环。核验实际运行进程、镜像、身份、挂载、固定出口、新 DSH home、Git 对象以及独立评分。故障场景涵盖错接受 SHA、越界写入、评分资料不可见和用量缺失。单写者隔离用于本次试点。计划引入跨 Host 并发前，用真实写者竞争和接管故障验证 fence。普通 Direct 流程也要在同一资格里证明无需正式任务就能交付。[接续运行入口](../../scripts/pnwf/energy/run.mjs) · [归因入口](../../scripts/psvr/session_attribution.mjs)

资格通过后，从同一冻结输入各执行一条 Palimpsest 与强原生 DSH 的软件项目周期，作为诊断试点。两边的提示只写业务成果、验证要求和审批条件。双方都可以使用 Git、原生 Subagent、Workflow 与测试。Palimpsest 从常规 DSH 产品入口启动，宿主负责环境、计量和独立判分。共同冻结模型、提示、输入变化、业务上的审核条件、会话窗口和判分器。审批按完整 SHA 核对，各自的人工操作与等待单列，后续会话只读各组已接受或适用的交付状态。首对计划沿用每个 Session 64 笔、30 分钟、单请求 240 秒的已验证窗口。付费运行使用本轮获准的模式和窗口。若授权要求硬上限，先验证真实 Provider 的可执行上界。

事先声明哪一步需要隔离和接受，两组按同样的业务边界判定合规。业务达标但未触发正式 Worker 的样本，分别记录业务达标与正式路径未采用。需要区分上下文和正式治理的贡献时，在强原生条件上加入从该组已有 Git 与项目事实生成的轻量上下文，沿用源文件权限并计入回显开销。

## 验收与停止条件

每个会话保留六个独立结论，记录 `PASS`、`FAIL` 或 `N/A` 及对应证据。文件存在用实际路径核对。业务正确用独立验收核对。资产持久化用完整 commit、blob 或等价的不可变引用核对。正式候选用 Attempt 结果和门禁核对。适用的接受用 Operator 决定、候选与接受 HEAD 核对。自然退出用进程终态和适用的结论核对。Direct 的结算和批准按适用性填写，`WAIT_FOR_OPERATOR` 只代表候选等待，`DELIVER` 仍要核对工件和内容。

| 待验证的作用 | 近端可观察证据 | 区分结果与替代解释 |
| --- | --- | --- |
| 项目连续性减少重新调查 | 新 Session 先取到绑定来源和版本的事实，仍有效成果保留，重复读取或重新生成的对象减少。 | 记录相同 path 与 blob 的重复读回，以及可复用成果被重做的次数。比较强原生 DSH，必要时加入同等源文件权限的轻量项目上下文。 |
| 独立发现改变后续工作 | 绑定来源的发现或反证出现，Principal 修改一个可定位的判断或计划，另一参与者据此改变文件、测试或结论。 | 按时间串起来源、角色、调用 ID、计划差异、Git diff 和独立验收。仅出现委派或时间相邻的事件时，继续检查是否有实际引用与修订。 |
| 治理提高受保护接受的可靠性 | Worker 的基线与写范围、真实结果、验证、批准和接受 HEAD 一致。 | 用错误 SHA、越界和旧依据故障注入验证拒绝。按场景对照原生 Git 审批，记录额外人工和工具步骤。 |
| 正常收尾降低协调开销 | 最终有用的 Git 产物出现后，状态提示走向合法交付或等待，会话自然结束。 | 配对结果、记录拒绝原因和失败作业，分开计数必要验证、状态轮询和同目标同原因的重复失败。 |

按完整项目周期保存所有已启动样本和全部角色的请求。分别报告 fresh input、cache read、cache creation、output、工具和宿主耗时、返工、人工修复及审批等待。重复读回按文件版本和调用 ID 计，返工按仍有效成果的重做和变更要求范围外的修订计。把阶段、调用和结果关联到独立验收。费用另按可核对的计费口径报告。对账缺失使用 `UNKNOWN`，保留已确认用量和现场，并停止后续付费会话。环境漂移、资料泄漏或资格失败降低比较效力。合法运行中的路径偏离、触发停止条件和业务失败计入结果。

首对样本用于定位能力采用和失败。发现方向性信号后，先冻结主要比较项，再按授权对每个领域独立复测，平衡两组先后顺序并单列首请求缓存。每域以三对有效样本为首轮门槛，至少两对在预先选定的指标同向改善，且质量和权限判据无退化，才进入下一轮工程验证。合法运行中的失败进入分母。比较条件失效的样本另行报告，样本不足时推迟结论。跨领域结论要求两个领域分别满足对应门槛。质量改善可用预先冻结的反例捕获或跨产物一致性通过来观察。质量相当时，优先比较返工和人工协调，其次解释用量。复测门槛用于选择下一步工程，完整分布、失败及不确定性随报告保留。

## 根据结果选择默认能力

| 后续观测 | 产品处置 |
| --- | --- |
| 轻量项目上下文保留了主要收益，正式 Work 的优势集中在隔离与接受。 | 默认呈现精简的项目现实，正式 Work 按风险使用。 |
| 真实合作让反例及时改变产物，或减少了可核对的返工。 | 优先改善发现进入计划、验证和后续复用的入口，再验证跨项目复用。 |
| 简单项目中原生 DSH 稳定等效，产品主要增加机械调用。 | 把这些任务交给直接路径，收缩默认工具和提示负担。 |
| 软件与 Energy 的重复配对都缺少质量或全周期收益。 | 保存负面结果，收窄价值主张到已证实的接续或治理场景，再决定投入。 |
