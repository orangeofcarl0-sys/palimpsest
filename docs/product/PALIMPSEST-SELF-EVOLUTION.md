Palimpsest 把自己的维护工作作为一个长期项目。当前稳定版读到新形成的运行证据，决定要不要立工单，自行提出并执行能检验原因的实验，分析结果，提交候选。经独立验证和授权的新版本接过同一维护项目，能从旧版留下的依据继续工作。用户给方向、权限和资源合同，Palimpsest 对选题、验证、修改和送审负责。

## 一轮由谁完成

| 阶段 | 发起者与动作 | 接续时能核对的事实 |
| --- | --- | --- |
| 接收证据 | 运行宿主封存实际结果，按运行 ID 和证据摘要投递待评估记录。重复投递归并到原记录，复跑归入发起它的工单。维护版决定立项、归并或保留观察。 | 原始流、账本、Git、已接受状态及首次提出问题的会话。证据不足时留下待求证项。 |
| 设计并实测 | 维护版提出可被推翻的解释，选最小复现和负控，按资源合同申请或执行实验。先留计划与判据，再读新结果。需要时自行请同伴调查。 | 假设与实验的先后顺序、谁发现反证、实际命令和调用结果、用量、基线 SHA、观测结果与未解决问题。 |
| 修订并送审 | 维护版用自己的候选分支管理代码与测试，从旧版上的预期失败验证到同一测试在候选上通过，再编写分析、提交和送审。结果不足时提交测量与后续判断。 | 候选完整 SHA、父提交、修改范围、回归结果与交付回执。由维护版完成 Git 操作，轨迹可追到实际提交。 |
| 独立验证 | 可信宿主从确切候选构建，使用冻结的独立判据和未向候选暴露的反例，验证原始问题、关键旧行为、持久状态读回与恢复。 | 完整候选 SHA、安装物摘要、依赖与运行配置、验收版本和结果、接受依据。候选自写测试作为证据之一。 |

所有者在开始前给出维护对象、目标、资源合同和晋升范围。维护版可以自行执行已授权的工作、建立候选分支和送审。首轮由所有者核准确切候选与安装物，可信启动器在候选工作区外核验授权并切换版本。连续接班得到验证后，所有者可预先授权一类可逆的维护发布，独立门禁通过即可切换。发布和用量权限、冻结判据及历史档案由可信宿主持有。`UNKNOWN`、验证失败和权限不符沿用各自的停止或等待路径，保留已完成事实。候选提出新的验收口径时，原判照旧保存，新的口径走独立审阅。

## 稳定版如何接班

先只给 Palimpsest 自维护项目设一个稳定运行位置。运行中的版本从固定安装物载入代码，维护工作写入隔离的候选副本。一次接受把候选 Git SHA、不可变的安装物摘要、运行环境与配置、状态版本、验证结果和授权记录绑在一起。后续启动读取这个已核验的版本。实现可以由已有宿主启动路径外的一层小型启动器承担。维护版继续使用 Work 和 Continuity，用户从同一项目的工作检查器核对版本接班所引用的证据。

1. **先验候选。** 在隔离状态副本运行实际打包构建。读回旧版的已接受事实、待办、未完工单和证据，验证它能启动并保存受控改动。绑定所用的完整 SHA 和安装物摘要。
2. **切换写入者。** 在旧版本的安全会话边界关闭新任务准入，等待旧写入者退出，封存参与接续的存储、账本状态和 Git 引用。以已核验的前代为条件，原子更新维护位置指向；新版本获取独占写入权后接续。重复触发或中断恢复读取已完成步骤，保留一次实际切换。
3. **观察接续。** 记录实际载入的安装物和前代状态。新会话从持久记录选择并推进下一项工作，留下可验的命令、测试或提交。单列候选已通过、安装物已激活、后继工作已发生三项事实。
4. **保留可用前代。** 新版尚未写入共享项目状态时，故障后可用最后一个一致的状态点恢复前代。已有新记录时，仅从含新记录且兼容的状态恢复；无法验证兼容时暂停写入并保留现场，按批准的恢复路径处理。故障反例实测启动中断、重放、版本错配和双写竞争。

### 独立验收

- **发现。** 轨迹显示维护版从原调用结果、Git 和持久状态判断“工件已提交、会话已自然退出，交付结论未记录”。它区分未调用、尝试后被拒绝、记录在别处等解释，并用实测缩小原因。外部通用目标没有点明 `DELIVER` 或要改的入口。
- **实验。** 维护版自己留下可复算的失败复现与通过复验，覆盖两条原轨迹所代表的状态。候选单独通过独立验收，包括合法的直接交付、已有结论、未完成或脏工作、需要等待所有者以及候选 SHA 绑定。修复机制可由模型选择。原评分、历史记录及治理边界按各自冻结合同核对。
- **送审。** 维护版完成问题登记、计划、数据整理、结论、源码和测试变更、Git 提交与候选送审。记录外部追加的指令、人工修补、核准动作和等待，各自计数。自主维护通过要求启动后的人类诊断提示和代写为零，允许预定的独立验收和所有者核准。
- **接班。** 接受版在隔离维护位置实际启动，先证明它读回了旧版的工单和原始依据，再由它选择并推进一张未提前展开的新维护工单。报告记录该版本实际使用了什么新能力、它如何改变工作，以及哪些效果仍需对照。两次稳定版切换并各自开展实际工作后，才确认自维护循环能重复运行。

## 实施顺序

1. 先做零付费资格。从封存结果触发普通 DSH，验证启动、证据投递、状态恢复、隔离执行、独立验收、安装物切换和故障恢复。脚本化 Mock 验证执行链和权威边界。模型是否自行发现、设计验证与合成成果由真实轨迹判定。
2. 资格通过并获得当轮运行授权后，按同一输入运行一次盲测，观察当前稳定版能否自己提出并送审冷交接修订。保存未完成、无法复现或结论相反的结果，供后继会话复用。
3. 独立验收通过、候选与构建获得核准后，接受版在隔离维护位置继续第二张真实维护工单。进一步核对前代经验是否被实际调用、是否减少返工，以及递进的版本能否继续接班。每轮分别记录质量、失败、请求与用量、耗时、人工介入和切换结果。维护项目的稳定发布策略由这些记录逐步推出。

这条路线以 Palimpsest 自己的工程工作检验里程碑二。多 Agent 的证据仍从实际反证、采纳决定和产物差异取得。长期自维护也允许 Principal 自行完成一张工单。
