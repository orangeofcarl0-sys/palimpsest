# 产品主路径与交互契约

## W1 — 第一次进入项目

输入：项目目录、目标、允许访问的来源与现有身份配置。结果：诊断依赖/权限，创建或加载 project，给出当前状态和下一步。不得要求用户手工建立五个数据库或在 Node 内调用 private function。

现有 profile 可保持专家配置；正常入口应由安装/doctor/init 安全生成，并说明路径与权限。缺少 authority 时明确其能力边界，不自动新建全能 operator。

## W2 — 继续已有项目

输入：“继续这个项目”。结果：读取持久状态，给出短摘要（accepted / candidate / negative / unresolved / blocked）、当前观察时间和相关来源入口。默认不倾倒所有 Event；不把信息压缩成失去来源的一句话；必要时按需展开。

成功：新 Session 完成一个正确下一步，不需开发者读内部 SQLite。若历史缺失，返回真实缺口，不生成假的已完成总结。

## W3 — 发现新现实

来源到达、用户目标修订、独立反证或失败实验触发局部重评。Agent 可以调查、记录候选结论、请求复核、提议任务。无关变化不应触发全部重规划。Source candidate 的可见性、可信性、是否被接受必须分开。

## W4 — 批准与行动

展示：具体行动、精确 payload/source digest、basis、scope、成本/风险、需要谁批准、可选拒绝或缩小范围。批准后调用既有 Work；批准拒绝/过期/重复时没有越权效果。创建 Task 不等于批准采购或源变更。

正常文案示例：
“该供应商公告尚未被项目接受。若采用，Site B 的当前选择会失效。可以先提交来源接纳请求；当前不能直接修改采购要求。”

## W5 — 成果提交与接受

Agent 完成工作后，产品观察真实执行世界、校验 scope/artifacts、导出真实 result object、验证适用性、呈现 review。模型不需要选择 arbitrary evidence predicate。未接受时明确：“已交付，尚未进入正式项目”。已接受时保留 resultCommit 与 acceptedHead 各自身份。

## W6 — 正确的负面成果

“没有合规方案”可以完成调查契约，但总体目标仍未实现。结果摘要包含工作完成状态、领域结论、证据充分性、未满足要求与后续选择。不得凭机械 SATISFIED 给项目打成功标签。也不把每个 negative 自动创建工作。

## W7 — 合作与合成

按需引入独立执行者。交接包含任务、限制、来源、当前依据、输出要求、风险和追溯入口。接收者必须能表示同意、条件采用、争议或需要复核。多个摘要重复同一来源不算独立证据。

用户只需要面对“为什么需要这次协作、得到什么、对项目改变了什么”，不需要配置固定角色拓扑。显式跨项目 Ask 不自动变为 commitment 或结果接受。

## W8 — 中断与恢复

区分 Session 恢复、Job 恢复、Work 状态恢复、外部效果对账。用户看到真实 running/waiting/review/uncertain 状态。结果丢失不能重建空 world 并装作从未工作。cancel 不等于撤销已经发生的外部效果；重复输入不得重复 Promotion。

## W9 — 日常简单任务

允许直接分析和文件级低风险结果。只在共享状态/正式效果需要时升级到强治理。拒绝“任何回答都必须创建 Work”。高风险效果不得借轻量模式绕过已有权限。
