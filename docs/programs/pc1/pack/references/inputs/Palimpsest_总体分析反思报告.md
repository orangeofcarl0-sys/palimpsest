# Palimpsest 总体分析与反思报告
## 从 Super-agent、从业者反馈与持久化 Harness，走向可持续修正的多 Agent 合成智能

**整理日期：2026 年 11 月 2 日**

## 摘要：这轮讨论最终改变了什么

这轮讨论的价值，不是找到了一种可以直接复制的“正确多 Agent 架构”，而是逐步改变了我们提出问题的方式。

最初的问题是：怎样把多个 Agent 组织起来，并降低人类协调成本？随后问题变成：怎样隔离局部认知负荷，同时保持跨任务连续性？继续深入，则变成：在模型调用并不天然保留长期经验的条件下，系统怎样维护当前有效的认识，并允许新现实修正旧判断？最后又出现了更高一层的问题：**如果架构本身决定系统看见什么、记住什么、怎样分工和怎样判断成功，那么架构自身是否也应当接受现实检验？**

本报告的核心判断是：

> **Palimpsest 不应把目标设为制造一个永不结束的主 Agent，而应探索：如何让有限、可替换的推理与执行过程，在持续变化的目标和环境中，形成具有连续身份、证据依据、修订能力和实际价值的共同成果。**

这不等于“把记忆放进数据库”，也不等于“给系统增加一个自我改进 Agent”。它要求同时处理三个不同问题：工作怎样持续；认识怎样更新；组织智能的方法怎样被检验。

因此，下一阶段最重要的不是再增加一层架构，而是证明：**现有可信基础是否真正改善了跨 Owner 的理解、协作、重规划与结果合成。** 在证明之前，复杂度应当受到约束；在证明之后，才值得将反复出现的需求固化为框架能力。

## 一、材料范围、证据等级与必要校正

本报告以用户提供的四篇评论合集、审稿人回应，以及此前围绕 Mario Zechner 帖子和 Palimpsest 愿景的讨论为主。为避免把先前分析中的推论继续当作事实，本次另外复核了 DSH 与 Pi Durable 的部分公开文档。

| 材料 | 可以支持的判断 | 不能直接支持的判断 |
|---|---|---|
| 《00_合集.md》四篇评论 | 作者提出了哪些观点、报告了哪些个人经验和失败模式 | 这些经验已经普遍成立，或构成严格对照实验 |
| 用户粘贴的审稿人回应 | 命名解释、团队所述设计动机、原型适用范围、未解决问题 | 对未来产品发布日期、规模化可靠性或全局最优性的保证 |
| Mario 帖子的可检索转引 | 他认可长期实体、临时自由委派、递归分工和跨系统事件这一方向 | 已经完成整套实现，或形成了正式合作、行业一致结论 |
| DSH、Pi Durable 公开文档 | 文档描述的对象、接口、恢复机制与明确限制 | 未经测试的生产成熟度、端到端正确性与性能优劣 |
| Palimpsest 项目对话 | 用户明确的愿景、历史上反复讨论的工程关注点 | 当前仓库已经实现并验证了本文提出的所有能力 |

**本报告不是对 Palimpsest 当前代码的重新审计。** 下面关于项目定位和下一阶段的判断属于设计反思，不能替代具体提交、实现和运行证据。

有四项尤其需要校正。

第一，**审稿人所说的“缺少跨 Session 长程记忆”，不能解读为 DSH 没有持久化会话。** 其 Session 文档已经描述追加式记录、历史重建、分叉和压缩；持久性取决于配置的后端。不能把 DSH 与 Pi 的区别简化为“一个不持久，一个持久”。[D4]

第二，**Pi Durable 是实验性基础设施，不是已被证明解决长期智能的成熟答案。** 文档明确标注 Experimental。持久化对话和任务可以改善恢复能力，但并不证明恢复后的目标理解正确。[P2]

第三，先前讨论中的精确延迟、缓存 Token 倍数、Router 利用率推算，以及部分产品内部架构推断，**不作为本报告的决策依据**。它们需要原始实验、版本和假设的独立核对；尤其不能从合成调度测试推导开放任务的智能合成能力。

第四，X 原帖在本次读取中仍无法直接展开。公开索引能找到对应文字，但没有系统核验其全部回复和引用讨论。这里把它作为有限的方向性材料，而非完整的讨论网络。[X1]

最重要的证据纪律是：**我们的前一轮解释，不会因为在后一轮被重复，就自动变成独立证据。**

## 二、各方真正贡献了什么：不是六套方案，而是六种观察位置

### 2.1 第一篇：Subagent 的主要价值可能是认知隔离，而非并行加速

某科学的仙人仉最有价值的表述，是“Subagent 的首要价值是改变 context topology”。他所描述的结构是：长期高层上下文，经由临时局部上下文产生资产，再压缩回流。[A，第一篇]

这一观察把问题从“增加多少 Agent”转向了“哪些细节应该由谁承担”。即使没有缩短完成时间，把局部调试、搜索与试错隔离出去，也可能使高层更稳定地维护目标、约束和关键决策。

但有三项不能直接接受为定律：平级协作并不等于独立采样；层级结构尚未被证明普遍优于其他拓扑；每一件微小工作都强制生成 Subagent，可能付出不必要的交接成本。

因此，值得保留的是**认知边界应当成为明确的设计对象**，而不是“一切都必须成为一个 Agent”的字面规则。

还有一个更重要的修正：人类的贡献不应被限定为事先写完整需求与验收标准。开放任务的目标往往在探索中才逐步清晰。系统必须支持这种共同发现，而不能把需求变化全部视为管理失误。

### 2.2 第二篇：长期系统的敌人不只是遗忘，还有过时认识

酱紫君描述的核心失败，不是 Router 完全不知道历史，而是它越来越难判断哪些历史要求已经失效。他提出的“昨天最紧急的事情不等于今天最紧急的事情”，揭示的是**时间变化下的判断有效性**。[A，第二篇]

他对链式召回的批评同样重要：有的模型过早停止，另一些模型不断追溯却迟迟不行动。两者共同指向的不是检索速度，而是“什么时候已有信息足以支持当前决策”。

其 Inline or Never 工作流值得作为一种上下文打包经验研究，但不宜升级为普遍禁令。禁止继续搜索会降低探索成本，也可能阻断新证据。随机更换模型、特定模型分工等做法，同样只能视为待验证的经验假设，不能作为品牌排名或架构常量。

更值得吸收的原则是：**把机械路由、语义判断与战略重规划分开；把高频分发交给明确关系，把复杂取舍交给有足够上下文和推理能力的决策过程。**

### 2.3 第三篇：减少打扰，不等于改善人的工作

赵泠提醒我们，人类注意力不是唯一目标。如果系统接走所有探索，把人变成不断点击批准的节点，工作可能更碎片化，也更缺乏意义。[A，第三篇]

这里应当保留的是产品判断，而不是未经重新核验的心理学数字：**应减少低价值协调，同时保留人的方向选择、创造性判断与理解进展的机会。**

她提出独立 Watchdog 的建议也值得研究，但运行监督和语义监督必须区分。进程是否存活可以有明确指标；工作是否值得继续，则需要结合目标、证据和不确定性。一个不断产出报告的 Agent 仍可能没有推进目标；一次失败实验反而可能排除关键错误方向。

### 2.4 第四篇：相似功能已经出现，不代表新工程没有价值

王Dao是也主要反对把已有产品形态重新包装成重大理论突破。这提供了必要的外部压力：不能只因为拥有新的对象名称和层级图，就认定产生了新能力。[A，第四篇]

但从交互表现或计费方式反推内部架构，仍然是推断；定时唤醒也不能直接等同于语义进展监督。本报告不沿用这些未经独立验证的等同关系。

对 Palimpsest 最重要的启发是：**价值需要与合理配置的现有系统比较，而不是与一个故意弱化的单 Agent 演示比较。** 新架构是否有用，最终要看有效成果、错误、成本与人类负担。

### 2.5 审稿人回应：简化条件本身就是设计的一部分

按用户提供的回应，“Super-”指在原本干活的 Agent 上方增加一层，不是宣称智能程度“超级”；团队承认相似架构已被其他团队探索，也明确说明原型依赖工程和场景简化。[B]

其中最重要的两个判断是：长程记忆尚无共识，促使团队处理连续性与吞吐量之间的权衡；代码原型越来越容易构建，但选择长期有效的方向仍然困难。

这里不能再向前多推一步，说双层架构已经是全局最优。更准确的理解是：它在一组已知边界内提供了合理分解。小规模、受信环境中成立的简化，扩大到跨组织、跨权限和高耦合任务时，需要重新评估。

### 2.6 Mario 与 Pi Durable：长期实体不必等于长期进程

Mario 可检索的帖子强调“single, long lived entity”，以及临时、自由、可能递归的委派。他表达的是方向趋同，不是一个已经完成的正式技术规范。[X1]

Pi Durable 的公开设计给这一方向提供了具体工程支点：任务检查点、可恢复对话，以及与对话记录一起提交的应用文档；同时保留实验性定位。[P1][P2]

这支持一个重要区分：**实体可以长期存在，承载它的进程和认知调用却可以结束、替换与重新启动。** 它并不进一步证明这些调用已经形成可靠的共同理解。

## 三、共同主线：长期 Agent 不是一个“记住一切”的聊天窗口

把这些材料放在一起，最有解释力的共同问题不是“树形还是网状”，而是：

> **怎样在局部认知隔离、工作并发、时间连续性和共同目标之间维持可用关系？**

以下几组区别应当成为后续讨论的基本词汇，而不是继续混用。

| 容易混淆的两件事 | 必须保留的区别 |
|---|---|
| 会话持续／工作持续 | 同一个聊天窗口不保证工作身份、承诺和结果连续 |
| 执行恢复／语义恢复 | 能继续运行，不代表应继续原来的方向 |
| 历史保存／当前认识 | 过去发生过，不代表今天仍然适用 |
| 上下文相关／行动授权 | 看见一条信息，不代表有权照它行动 |
| 输出正确／当前可接受 | 局部正确的成果，可能基于已经失效的目标或前提 |
| 多个结果／智能合成 | 汇总产出，不等于识别冲突并形成更好的共同决策 |
| 策略改变／经验学习 | 系统发生变化，不代表变化可重复地改善结果 |

DSH 的 Ticket 与 Assignment 分离，以及 Mandate 对授权范围的表达，说明其中一些边界可以进入明确的工作模型。[D1] 但这些对象不应被直接复制到 Palimpsest；应先检查已有 Owner、工作和资产语义是否已经表达同一职责。

真正值得稳定下来的，是这些区别，而不是某套框架恰好使用的类名。

## 四、模型“无状态”意味着什么，又不意味着什么

### 4.1 应当把前提说准确

这里的“无状态”，应限定为：**在固定模型参数的常见推理调用方式下，一次调用获得的新经历，不会自动成为后续独立调用都能使用的持久经验；历史需要由上下文、外部存储或服务层机制带入。** Anthropic 的 Messages API 明确以 stateless 描述接口，要求调用方提供对话历史。[M1]

这不是说模型没有参数知识，也不是说一次推理内部没有计算状态，更不是说所有服务端产品都不保存会话。

由此得到的不是“长期智能不可能”，而是一个责任转移：**跨时间连续性必须由整个系统承载，不能默认为单次模型推理自带的性质。**

### 4.2 状态外置只解决了保存位置，没有解决保存内容

把聊天历史放进数据库，可以让记录存在；却没有回答哪些内容应该进入下一次调用、哪些已被推翻、哪些仍有争议，以及哪些只对特定条件成立。

因此，核心问题不是“有没有 Memory”，而是**怎样构造当前可用的认识**。

可以用一个概念模型表示：

```text
持久历史 + 当前承诺 + 新观察
          ↓ 按任务、权限、相关性构造上下文
       一次模型推理
          ↓ 产生行动或判断候选
    执行、取证、验证与接受
          ↓
更新工作状态与当前认识；必要时重新组织工作
```

这里最容易被忽略的两个环节，是“构造上下文”和“接受变化”。前者决定模型看见什么，后者决定哪些输出能够影响未来。两者都包含可能出错的判断，不能因为位于模型之外，就被视为天然可靠。

### 4.3 持久的应当是承诺，不只是文本

一个长期协作实体需要保持的，至少包括当前目标、尚未完成的工作、已经作出的决定、授权范围、已采用成果及其依据，以及仍未解决的不确定性。

下一次推理可以由另一个模型、另一个 Session 或另一个执行实例承担；但它需要知道自己继承了哪些承诺，以及哪些部分有权重新判断。

这比维持同一人设或聊天语气更接近工作连续性的实质。

同时，可重建不等于可逐字复现。即使输入相同，新的模型调用也未必产生相同判断。因此，应该保留关键输入、版本、工具结果与接受记录，而不是把重新调用模型当作历史重放的等价替代。

### 4.4 无状态性不是唯一根因

不能把所有长期失败都归结于模型无状态。即使有可靠记忆，系统仍然面对目标歧义、资源限制、外部副作用、权限边界和互相矛盾的证据。

因此，Palimpsest 不应把“解决记忆”当成解决一切的总钥匙。更准确的目标是：**在有限认知与不完整观察下，维持可检查、可修订的工作连续性。**

## 五、Context Topology：组织的不是 Agent 名字，而是信息与判断

### 5.1 低上下文负担，不等于低推理难度

第一篇希望 Leader 不被执行细节占满；第二篇认为高层调度可能需要最强判断。二者并不矛盾。

一个高层决策者可以只看少量信息，却处理最困难的取舍。应该减少的是无关细节，而不是降低决策质量。

因此，固定订阅关系可以由程序分发；新的工作请求需要语义识别；目标冲突、依赖变化和资源取舍，则需要较完整的战略上下文。不能把三者混称 Router，然后为它们统一选择模型与预算。

### 5.2 三种关系不必共享一张图

委派关系回答谁负责什么、谁可以授予哪些任务；信息关系回答谁需要看见哪些证据；依赖关系回答某个判断变化后，哪些成果需要重评。

委派可以是树形，信息交换可以跨层级，依赖可以形成跨 Owner 的网络。强迫它们完全一致，会把组织便利误当成问题本身的结构。

这也解释了为什么“层级一定优于平级”过于绝对。层级有利于责任归属和局部压缩；独立研究有利于减少共同前提；直接协商有利于处理高耦合问题。应当比较它们在具体任务上的收益，而不是先宣布一种普遍优越的拓扑。

### 5.3 摘要不是无损接口

只回传短报告，可以减轻上层负担，但局部 Agent 未必知道哪些细节将在未来变得重要。

因此，交接不宜只有结论，也不宜复制全部日志。一个可操作的最小交接面是：**成果、适用前提、关键证据、尚未解决的风险、需要上层决定的事项，以及按需追溯的入口。**

这里要求保留的是可观察的操作与证据，不是把模型内部思维链当作证明材料。

### 5.4 自发合作应当意味着可受约束的主动性

Owner 可以发现新工作、请求帮助、提出分工调整、暴露冲突；但不能因递归委派而自动扩大授权或预算。

“自由组织”不意味着无限创建 Agent，也不意味着每个 Agent 都可以修改共同目标。更合理的原则是：**组织可以临时形成，责任、权限和结果接受边界不能随之消失。**

## 六、Temporal Reality：系统必须能够摆脱过去正确、现在错误的判断

### 6.1 记住历史与理解变化是两个问题

假设路线 A 在条件 X 下被否定。后来 X 被取消，系统就需要重新评估 A，而不能把“过去曾否定 A”当作永远有效的结论。

反过来，一个在旧约束下已经完成的成果，也可能因新约束而失去适用性。

所以，长期认识至少应能表达：结论针对什么条件、依据什么证据、何时形成、被什么后续事实影响，以及当前是否仍可用于决策。

不需要一开始就建立通用形式逻辑。先为高影响决定保留这些信息，就比只保存“已完成”有意义。

### 6.2 Reality 应当是可修订的认识投影，不是绝对真相

应区别三件事：实验观察到了什么；系统怎样解释观察；系统因此决定怎样行动。

“测量结果下降”是观察；“方案不适用”是解释；“停止该方向”是决定。它们不应该合并成一条没有条件的事实。

因此，Palimpsest 的 Accepted State 更适合理解为**当前有依据、在指定范围内被采用的项目承诺**，而不是不可推翻的真理。

接受可以允许行动，但必须保留来源、适用范围和重开判断的条件。争议、未知和证据不足也应该有合法位置，不能为了生成一个整洁的全局状态而被消除。

### 6.3 迟到结果的正确处理

当目标或依赖版本改变后，旧 Worker 的结果可能仍是有价值的历史证据，但不一定能进入当前状态。

正确处理应是重新检查其所依据的目标、授权、输入资产与验证环境，再决定采纳、部分复用、重新验证或保留而不采用。

**取消旧任务是资源管理；阻止旧结果错误生效是状态管理。** 两者都需要，不能互相替代。

对于并发接受，检查与写入也必须协调：若检查通过之后依赖又发生变化，就需要在接受时再次核对，或通过明确的事务与版本条件阻止失效写入。

### 6.4 优先级应当带有重新判断的理由

优先级不是任务永久不变的标签。它应受当前目标、依赖、时间窗口、资源和机会成本影响。

但也不应每来一条消息就全局重规划。更可控的做法是识别能够改变计划的事件：目标修订、关键反证、依赖失效、资源变化或长期停滞，再启动适当范围的重评。

重要的不是系统总在规划，而是它**知道什么时候原来的计划不再足够可信**。

## 七、长期记忆与 Trajectory：从“更多历史”转向“可重建的当前理解”

### 7.1 三层信息，而不是一个无限膨胀的总文档

建议把历史依据、当前投影和任务上下文包区分开。

历史依据保存必要的原始事件、产物和关键观察；当前投影表达已采用的目标、决定、事实与争议；任务上下文包则根据本次工作，提供局部足够的目标、约束、证据与入口。

这吸收了 Inline or Never 的优势——减少 Worker 在碎片中迷失——但不禁止发现缺口后继续检索，也不让摘要覆盖原始依据。

这些是信息职责，不意味着必须立刻新建三套存储系统。

### 7.2 检索需要针对判断的停止条件

“还能继续找到内容”不是检索的目的。应先明确当前要判断什么，哪些证据必须覆盖，什么缺口会改变行动。

高影响、不可逆决定应要求更强的证据；可逆试验则可以在明确不确定性的情况下先行动。无法补足的缺口，应导致缩小行动范围、保留未知或请求判断，而不是凭自信结束检索。

这里的“证据充分性”是工作契约，不是通用真理证明器。系统只能检验指定问题下的证据要求，不能宣布已经穷尽现实。

### 7.3 Trajectory 的合理边界

根据项目此前明确的方向，Trajectory 最值得承担的是：项目演化历史、关键接受与拒绝的依据、跨 Owner 的影响关系，以及当前理解需要回溯的入口。

它不应自然膨胀为第二个 Planner、万能检索器、所有业务知识的统一表示，或独立于 Harness 的完整 Agent 运行时。

最有价值的接口不是“返回全部历史”，而是回答：**当前决定依赖什么；哪些依据发生了变化；哪些工作因此需要被重新看见。**

影响判断也可以是不确定的。将“可能受影响”明确交给 Agent 重评，比用不完整规则自动宣布所有语义依赖都已计算正确更诚实。

### 7.4 必须防止系统用自己的总结证明自己

一个非常具体的补充例子来自 Pi Durable 的 Cloudflare 演示：历史搜索子 Agent 不搜索自己和先前搜索生成的结果，避免生成的搜索结论再次成为后续搜索的证据。[P3]

这不能直接推广为整个项目的成熟认识论，但提供了值得吸收的规则：**派生摘要必须保留来源身份，不能因重复出现就增加独立证据权重。**

同样，本报告提出的术语和推论，在未被实验支持之前，都只能作为研究假设保存，不能被后续 Agent 当作项目已经证明的事实。

## 八、最深的 Spark：架构决策也是可以被现实推翻的假设

### 8.1 为什么它与无状态模型直接相关

当模型每次推理依赖系统提供的上下文与工具时，系统的架构就持续决定：什么进入上下文、哪些历史被省略、谁能交流、何时调用更强模型，以及何种结果能够影响后续工作。

这些选择会跨越单次模型调用持续生效。

因此，从系统行为角度看，架构不只是中性的容器，也是一组长期生效的组织假设。例如：“这些任务通常可以独立完成”“短摘要足够支持上层判断”“一个协调者能够看清全局”。

如果现实不断否定这些假设，只让 Worker 修改 Prompt 或重试，并不能纠正根本问题。

### 8.2 两个不同速度的反馈循环

任务循环是：目标驱动行动，行动产生证据，证据改变当前认识和下一步计划。

组织循环是：某种分工与信息结构产生结果，结果揭示其收益和失效条件，再通过比较决定是否调整组织方式。

第二个循环不必一开始就自动化，更不必立即变成自修改代码。人工维护设计假设、让 Agent 识别失效信号、受控试验替代策略，都属于有效起点。

### 8.3 四个层次不能混称“学习”

| 层次 | 发生了什么 | 还需要什么才能证明价值 |
|---|---|---|
| 记录经验 | 留下事件与结果 | 证明未来能够正确利用 |
| 修正认识 | 改变当前目标解释或事实判断 | 证明修正有依据且改善决策 |
| 调整策略 | 改变检索、委派、模型选择或协作方式 | 在可比任务上检验收益与代价 |
| 调整架构 | 修改长期组织假设、边界或协议 | 验证迁移、安全性及跨任务效果 |

系统可以不更新模型权重，却通过外部策略形成更好的表现。但要称为系统层面的经验学习，至少需要证明改进不是一次偶然成功，也不是通过降低验收要求获得。

**热更新能力证明系统能变，不证明它知道怎样变得更好。**

### 8.4 架构还决定了系统能发现哪些问题

如果只记录任务完成数量，系统可能发现效率下降，却发现不了大量“完成”的任务建立在同一个错误前提上。

因此，架构自评有封闭风险：它可能只使用自己允许记录的指标，为自己辩护。

应保留外部结果评价、用户异议、独立审查与不适合现有分类的异常记录。尤其要允许系统说：“这次失败可能暴露了我们的表示方式不够，而不是某个任务执行不够好。”

这种开放性是研究要求，不是立即增加一个万能元模型的理由。

### 8.5 必须允许新架构实验失败

如果固定层级已经足够，动态拓扑就不应该为了“更智能”而被保留；如果普通文档交接达到同等效果，复杂状态层就需要缩减；如果额外审查者只增加成本而不改善结果，就应该撤掉。

真正接受现实反馈，也包括**接受现实没有支持我们最喜欢的架构思想**。

## 九、可塑性与可信性：允许变化，但不能允许成功标准随失败漂移

### 9.1 应区分变化频率

工作状态可以高频变化；协作策略可以受控调整；身份、权限、证据来源、接受与撤销规则则应低频、显式地升级。

这里的“可信内核”不是永远不变，而是不允许某个执行者为了完成眼前任务，临时改写自己必须满足的规则。

尤其要区分：修正不合理验收要求，与为了让现有结果通过而降低要求。前者需要有权主体确认、保留理由，并使新旧结果的比较仍然可解释。

### 9.2 持久化与 exactly-once 必须限定范围

DSH 文档描述了先记录工作、后执行，以及失败恢复时检查外部实际状态；Pi Durable 区分可安全重放的工具与被中断的工具调用。[D2][P2]

这些机制不自动解决跨外部平台的所有重复副作用。若操作已成功、回执尚未保存时崩溃，本地日志可能无法单独判定是否应重试。

需要结合外部幂等标识、结果查询、对账或显式的未知状态处理。系统不应为了让任务状态整齐，就把未知解释为失败或成功。

此外，逻辑上拒绝一个迟到结果，也不能撤销它已经发送的邮件、发布的内容或修改的外部资源。因此，工具权限与实际副作用控制必须发生在执行路径上，不能全部推给事后的成果验收。

### 9.3 原子一致不等于语义正确

对话记录与应用状态共同提交，能防止一部分存储不一致；却不能保证写入的解释真实。模型给出错误判断，再与状态一起原子保存，只会得到一个一致地保存了错误的系统。

所以必须保留两个独立问题：记录是否完整一致；判断是否有足够依据。

## 十、Palimpsest 的定位：既不能退化为资产管理器，也不应重造整个 Harness

### 10.1 愿景应当保留

用户明确的愿景仍然是：

> **项目可信资产管理 + Agent 自发合作 + Top-Down Intent & Bottom-Up Reality = 面向长程大型任务的多 Agent 智能合成。**

三者不可互相替代。只有可信资产，会成为可靠但可能沉重的工作记录系统；只有自主协作，可能只是动态编排；只有模型汇总，则可能产生漂亮但没有共同依据的叙述。

Palimpsest 应证明三者结合后，能够更好地发现冲突、修改错误前提、重新分工，并形成可采用成果。

### 10.2 与 DSH、Pi 的关系应按责任区分，而不是排高低

DSH Super-agent 的公开模型重点表达事件如何成为有授权的工作，以及工作与执行实例怎样分离；Pi Durable 重点提供持久任务、对话和应用状态的运行基础。[D1][P1]

但二者都有恢复、上下文和执行方面的交集，不能把前者说成只有业务语义、后者说成只有底层存储。

Palimpsest 的候选差异，是围绕共同目标、共享成果、证据依赖和跨 Owner 合成建立应用级能力。**这是需要验证的定位，不是已被证明的优势。**

### 10.3 建议的工程取舍

| 类别 | 当前建议 | 判断依据 |
|---|---|---|
| 通用模型调用、工具执行、Session 与基础恢复 | 尽量复用现有 Harness | 避免重复建设，不预设立即迁移框架 |
| Owner、工作身份、候选成果与接受边界 | 保留有实际作用的已有机制 | 是异步协作与责任连续性的基础 |
| Intent 修订、证据适用条件、受影响工作识别 | 作为下一轮最小闭环的重点 | 直接检验长期目标变化下的合成能力 |
| Trajectory | 保持项目演化与因果投影定位 | 不扩张为万能认知与调度层 |
| 动态拓扑、强自治 Watchdog、架构自修改 | 先作为受控实验 | 缺少收益证据时不应成为核心依赖 |
| 通用 A2A 网络、全面跨云运行时 | 暂不因行业热度而优先建设 | 需先证明实际任务产生了相应瓶颈 |

这不否定此前严格工程工作的价值，而是要求它们进入一个真实的用户价值闭环。

### 10.4 Git 是重要适配，不应成为通用愿景的全部语义

Git 对象能提供稳定身份和版本关系，却不能单独判断报告、实验结论或设计方案是否成立。

跨领域时，应保持“工作—证据—候选成果—接受”的职责区分，让验证方式由领域决定。代码可以用测试和审查；研究需要实验与来源；开放式方案可能需要独立评估和人类取舍。

并非所有资产都必须得到二元的“真／假”判定。带条件采用、暂缓、保留争议或仅作为观察，都可能是合理结果。

## 十一、下一阶段应当证明什么：一个端到端场景与分层对照

### 11.1 场景应同时包含认知变化与工程故障

建议先使用一个可控的非纯编码场景：**在给定资源与约束下，形成并验证一套研究或技术验证方案。** 下面是实验设计，不是已经完成的结果。

三个 Owner 分别研究候选方法、验证关键假设、分析资源和交付条件。随后引入几种事件：新实验否定共同前提；用户修改一项关键目标；一个仍基于旧条件的任务迟到返回；两份报告出现实质冲突；执行过程中发生重启和重复输入。

系统最终不能只是把三份报告拼接起来。它需要识别哪些结论仍有效，决定哪些工作保留、重做或停止，必要时启动针对性协商，并给出当前条件下有依据的方案。

人的介入应集中于无法代替人的价值取舍，而不是让人手工拼回上下文。

可控版本应有事先设计的事实变化和判定规则；随后再进入开放任务，评估真实解释质量与用户价值。两者互补，不能用一种代替另一种。

### 11.2 对照组不能故意削弱基线

| 组别 | 配置 | 用途 |
|---|---|---|
| A | 合理提示的单主 Agent，可使用 Subagent | 检查复杂系统是否胜过强简单基线 |
| B | 有持久任务、正常摘要交接的 Router/Worker | 排除基础并发与恢复能力带来的收益 |
| C | B 加上最小的 Intent 修订、证据依赖和成果接受机制 | 检验 Palimpsest 项目语义的额外价值 |
| D | C 再允许按明确条件调整局部协作方式 | 检验组织适应是否值得其成本 |

C 不优于 B，就应检查项目语义层是否过重或没有针对真实瓶颈。D 不优于 C，就不应默认保留动态拓扑。

### 11.3 指标必须同时覆盖正确性和价值

主要结果应是当前目标满足程度、有效采用的成果质量，以及人类为得到这些成果付出的工作。

诊断指标包括过时成果误用、关键依赖遗漏、证据错误引用、授权越界、冲突是否解决、无效重试、无价值通知、验收时间及总体计算成本。

任务完成数量、Token 数和延迟可以解释机制，但不能单独代表系统价值。失败实验也可能贡献重要知识，应由任务评价区分“没有产出”和“产生了有价值的否定结果”。

### 11.4 实验纪律

应控制模型与工具能力，记录总预算并把协调、审查和额外检索的成本算入。使用可比任务和事件扰动，保留失败、超时与未完成案例；测试新任务，而不是只在反复调过的样例上展示提升。

冻结实现版本、配置、数据和环境，随后单独冻结结果与证据。代码任务继续保留候选、结果与接受身份的区分；非代码任务保留等价的来源和版本关联。

少量运行中没有出现严重错误，只能说明这些运行未观察到错误，不能证明错误概率为零。生产力提升也应报告波动和任务范围，而不是凭一次成功宣布普遍优越。

## 十二、对我们自身讨论与工程方法的反思

### 12.1 不能用新名词替代新能力

Context Topology、当前现实投影、证据充分性、架构适应都可以帮助分析，但它们首先是问题划分，不是应该立即创建的核心实体。

每引入一个抽象，都应回答：现有对象为什么表达不了？它减少了哪种实际错误？不用它的基线是什么？它又增加了多少状态同步和维护成本？

答不清时，先保留在设计假设或实验记录中，不急于进入核心代码。

### 12.2 不能把“更可信”自动等同于“更智能”

可信机制可以降低错误接受、丢失与重试歧义，却不会自动让 Agent 发现更好的方法。

反过来，生成新想法也不意味着它可以安全成为共同成果。

Palimpsest 应同时证明合成质量与接受可靠性，而不是选择其中一项作为另一项的替代证明。

### 12.3 不能让已有工程路径永久决定下一步

如果当前主要瓶颈已是跨 Owner 理解与合成，那么继续打磨低风险边界，可能不如完成一次真实闭环有价值。

但“不要过度工程”也不能成为删除必要安全边界的理由。应当先识别哪些约束直接保护真实工作，再削减没有实际收益的重复机制。

### 12.4 不要把个人经验升级为普遍模型规律

某模型更适合规划、另一模型更适合执行，可能与提示词、任务分布、工具和使用者习惯有关。模型多样性只有在带来互补且可测量的错误模式时才值得保留。

同理，“重开 Session 更好”“层级一定更稳”“全部内联更高效”都应保留为可检验假设，而非默认公理。

### 12.5 不要把自适应理解为无限自我授权

从发现某种组织失效，到提出替代方式，再到运行小规模比较，最后采用新策略，中间应有清晰边界。

系统可以建议改变自身，但不因此获得修改权限、抹去历史、重定义验收或无限消耗资源的权力。

### 12.6 人类不是只剩下审批的外部验证器

人可以修改目标、理解新发现、参与探索，并选择系统不能代替其决定的取舍。用户改变想法不总是噪音，也可能是系统工作产生价值的结果。

因此，产品应支持不同深度的参与，而不是仅提供“完全自动”和“每步审批”两个极端。

## 十三、收敛后的决策与最终结论

现阶段最明确的取舍是：**保留愿景，收窄下一轮实现范围；保留必要可信边界，把主要验证对象转向真实合成；把架构适应作为可证伪的研究假设，而不是立即建设自修改系统。**

下一阶段的主问题可以压缩为：

> **当目标、证据或依赖发生变化时，Palimpsest 能否让多个 Owner 在较少人工协调下，识别旧认识的失效，重新组织必要工作，并形成更可靠、更有价值的共同成果？**

这里还应加入一个反向要求：变化不重要时，系统能否保持稳定，不因每条新信息都无谓重规划、重开 Agent 或重做工作？真正的适应既包括及时改变，也包括有依据地不变。

这轮材料最终支持的，不是某个固定层级已经成为答案，而是几个需要长期保持的工程原则：工作身份应独立于执行实例；上下文边界值得明确设计；历史需要经过当前有效性判断；已有架构应当保留被现实否定的可能；而任何更复杂的机制都应通过真实收益证明必要性。

**模型调用的无状态性，使长期连续性必须由系统组织；但系统保存了状态，并不意味着它就学会了经验。** 只有当经验能够有依据地改变未来判断，并在新任务中体现出可重复的价值，才能谈系统层面的学习。

因此，Palimpsest 最值得追求的不是“永远记住”，而是：

> **让工作持续，让认识可修正，让合作产生额外价值，并让组织合作的方法本身接受现实检验。**

这既保留了项目可信资产与 Trajectory 的意义，也把它们放回更大的目标中：它们不是项目的终点，而是让多个有限智能过程能够持续形成可靠共同成果的条件。
