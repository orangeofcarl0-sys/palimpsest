# Fleet 夜班交接：一次误报，还是一次回退？

## 上一轮实际测到了什么

真实模型在序号 45–50 连续读取了已经按站点归一的资料，在 89 和 91 写出清单和报告，再在 97 用一个 Node 程序枚举并验证组合。设备版本、冲突时谁优先、目标函数和输出格式都已给定。模型需要做的工作可以压成一张小表。Mock 中的三名子会话各计算一列，彼此的答案不会改变对方下一步要问的问题。上轮有跨资料合成，有脚本化分工；真实轨迹有一个 Principal、零个子会话、零条贡献决定。这个结果与任务结构相符。单个样本不足以区分模型偏好与任务条件。[真实逐调用记录](../../research-evidence/pnwf-software/2026-11-19/fleet-rollout/live/out/ROLLOUT/attribution/0.timeline.json)

本轮要观察一个更窄、也更有价值的问题：当一个人拟定的修复会破坏另一个人发现的正常行为时，他们会不会主动寻求彼此的判断，交回可复现的反例，然后共同改变工程成果和现场安排？有价值的合作也可能发生在否决一个错误补丁、保留原实现或收窄承诺范围时。

## 一次可能发生的合作

以下是采样前写下的预期交互。实际模型是否选择这条路径，见[普通 DSH 配对观察](FLEET-NIGHT-SHIFT-PAIR.md)。

1. 初稿以“重试导致重复”为工作假设，提出全局去重。实现者可以独立完成，也可以让人拿一个会误删正常事件的例子回来。
2. 复核者用 Alder 的 p04、p09 交回两个相同请求号的合法绘制。实现者据此改变数据键，并回问“Birch 第二次究竟有没有画到屏上”。现场调查者须先校准别名，再把请求和终端事件配起来。只把三段总结拼起来解释不了这处修改。
3. 一条有辨识力的证据是同一块 p17 的绘制序列。若为 40、41、40，就能复现局部倒退；若为 40、41，随后收到抑制事件，则这次重试没有重绘。两种情形的运营动作可能都很谨慎，证据陈述和恢复条件仍应不同。
4. 技术建议若要求 06:10Z 把 Birch 导到备用通道，排班台会对确切方案返回预约冲突。参与者可以改成局部暂停，或在 06:30Z 以后申请共享通道。收到排班回执是外部反馈。若另一 Agent 将它与 p23 的覆盖缺口联系起来，指出原方案会让一个没有观测的站点静默上线，并让团队修改交接稿，这一段才有跨参与者判断的证据。

已有两个草案、两项研究任务或三名 Agent 并不自动构成上述过程。允许全程独立，也允许调查者推翻 Principal 后，Principal 用新的回放再推翻调查者。

### 让合作对象有自己的工作历史

仅仅让同一个模型多查五个档案，仍很可能重现上轮独立解题。更接近实际团队的实验条件是让**上一班做过事的人仍可被找回**。例如，一名参与者在前一班真正维护过放行检查，能说明它当时为何只看 RPC；另一名参与者曾用双屏回放验收过调度台，手上有一个以前通过的正常样例。各自的旧提交、失败尝试和当时不知道的事都按 SHA 留痕。不要在角色描述里提前写入夜班答案。新 Principal 可自行追读这些档案，也可把新草案和一个具体疑问发给原参与者。对方能在隔离副本里试跑当前改动，提出意料之外的反例，或承认旧经验已不适用。

观察中尤其值得保留的是**第二次往返**：例如旧维护者建议去重，现场参与者用正常双屏反驳，维护者再改验收条件，Principal 因此收窄早班承诺。这种往返产生的新测试或新决定，无法通过统计发出了几次查询来识别。保留不同参与者只读相同资料后给出相同结论的负例。持续参与者条件需先有真实上一班轨迹，其收益与冷启动子会话条件分别比较。当前本地夹具提供的是两边可共用的业务世界。

## 事件安排、权限与对照

- **第一班。** 仅挂载 world/。两种事先冻结的世界有字节相同的初始 Git 树及完整提交 SHA。先留下初步判断和可逆安排；若模型拒绝过早定因，保留这份正确的谨慎。交班以首份已提交的 Markdown 评估为界，与调用了几个 Agent 无关。
- **第二班。** 桌面档案开放五类查询，任何参与者都能获得相同资料，可一次拿齐或按假设调取。宿主侧保存查询主题、文件摘要及初稿 SHA。预约试排绑定当前方案的 Git blob 和完整提交，冲突会给出具体理由。宿主响应和其他 Agent 的判断分别归因。
- **成对设计。** 在重绘与抑制两个世界，各做“允许自主协作”和“单 Principal、自主工具受同等条件约束”的配对。保留同一输入、检查点、总请求/时间窗、可发起的业务查询和最终验收。两组都能独自调查、编程和申请试排。不同世界和不同组使用全新会话与互不可见的状态。只在需要定位介入机制时加明确分工组，单列其结果。
- **模糊性保留给业务，实验条件由宿主固定。** 频率偏好、演示损失和缺失面板允许条件式决定。能被回放证伪的事实严格核对。评阅者先看去掉角色信息的提交与现场建议，再揭开轨迹评协作。短时间窗和子任务计入总量也可能降低委派意愿，应记录在案。单份正例可支持“发生过”，跨组的稳定收益需更多独立重复。

## 如何评分

| 维度 | 核验对象与边界 |
| --- | --- |
| 现场事实 | 对应世界的 p17 行为、p23 无数据、训练屏归属、同请求在 Alder 双屏合法、Cedar 的预约时段。陈述“整个 Birch 安全”或“整个 Birch 都倒退”均超过证据。 |
| 技术成果 | 用提交中的回放或测试在隔离副本重放两种终端记录；检查异常、正常重试和 Alder 双屏。允许修判据、加一个诊断测试、或在证据支持时保留现有服务代码。旧看板单独只覆盖 RPC 错误率。 |
| 业务取舍 | 强约束是通道不重复分配、生产权限留给所有者和覆盖不足时显式限定结论。保守暂停、有限继续或延期均可成立。比较撤销条件、保留的服务范围和遗留风险；不设唯一标准文本。 |
| 合作发生 | 原生父子会话/正式作业及其真实调用结果能定位；对方交回一项可证伪发现；接收方能定位对它的检验、质疑或决定；随后确切 Git 差异改变了测试、代码或处置。将“共同调查”“独立交付后被确认”“采纳后修改”“依据不足”分别记。 |
| 合作收益 | 和同世界的独立路径比较业务漏项、正常行为被破坏数、作废返工、人工接管、墙钟及逐角色用量。两边同样正确时只报告这些具体差异。 |

宿主应同时保存草稿 SHA、父子会话 ID、消息与回执 ID、证据首次可见时间、修改前后 blob、试排回执和最终原稿。若初稿早已含同一处修复，仅支持“后来确认”。若两边同时取得档案、主会话早已自行复现、又无法追到对方带来的变化，则归因留空。即便看到了按序发生的采纳与改动，单条轨迹也不能证明没有该 Agent 就一定做不到。

## 哪些能力需要用别的任务检验

夜班案擅长检验反例能否改变工程与运营判断。它仍有可以查清的设备事实。要考察团队能否共同定义问题，还需要结构不同的案例。以下两项是后续设计备选。

| 案例 | 任务和资料 | 怎样观察实质合作 |
| --- | --- | --- |
| **重新设计交班界面** | 调度员只说“不要让我交错班”。三份走查记录分别来自白班、夜班和培训班，旧截图中两种状态同色。可用性、培训成本和审计可追溯性互相牵制，需求方自己也没确定正确交互。提交可走查的原型，并让接班人用它处理陌生案例。 | 观察研究者指出原型会诱发的具体误读，设计者据此修改交互；再观察修改是否让另一类用户多走一步。用陌生案例的错误交接数与完成时间验证，不按页面长相或评审赞同票打分。 |
| **区域换机与客户承诺重谈** | 库存表混有已预留件，供应商邮件把“到仓”称作“交付”，现场技师节假日只有半班。已有承诺相互冲突，一家客户尚未确认能否停机。既要给临时排程，又要写得出能改变排程的澄清问题。 | 排程者提出分批方案；现场复核者发现两批实际争用同一校准台；商务参与者重拟客户承诺，现场再验证新停机窗。核对修改后的工单、对外文本及保留条件是否一致，接受多种可兑现方案。 |

这两类任务分别把不确定性放在“用户究竟需要什么”和“多方愿意承诺什么”。它们与夜班案可共享轨迹取证方法，各自保留独立的业务验收。
